# Архитектурное решение по кешированию

## 1. Мотивация

В системе MES наблюдаются проблемы с производительностью: операторы жалуются на долгую загрузку дашборда со списком заказов. Фильтрация и пагинация не дали эффекта, что указывает на высокую нагрузку при чтении данных из БД.

Основные проблемы:

* медленная загрузка списка заказов;
* высокая нагрузка на MES DB;
* задержка появления новых заказов для операторов;
* ухудшение пользовательского опыта.

Кеширование должно:

* ускорить чтение данных;
* снизить нагрузку на базу;
* обеспечить быстрый доступ к новым заказам;
* стабилизировать систему при росте нагрузки.

Кешируются:

* список заказов по статусам;
* первая страница новых заказов;
* агрегаты (количество заказов по статусам).

Не кешируются:

* расчёт стоимости;
* критичные транзакции.

---

## 2. Предлагаемое решение

Тип кеширования: серверное.

Технология:

* Redis — внешний кеш;
* MES API — работа с кешем;
* MES DB — источник истины.

Паттерн: **Write-Through**

### Почему Write-Through

* при изменении статуса данные записываются в MES DB и сразу обновляют Redis;
* кеш остаётся согласованным с БД;
* чтение дашборда происходит из актуального кеша;
* уменьшается количество тяжёлых запросов к БД.

### Почему не Cache-Aside

* при частых изменениях статусов возникают частые cache miss;
* увеличивается нагрузка на БД;
* возможна временная несогласованность данных.

### Почему не Refresh-Ahead

* сложнее в реализации;
* требует фоновых задач и анализа паттернов доступа;
* избыточен для MVP.

---

## 3. Ключи кеша

```text
mes:orders:status:{status}:page:{page}:size:{size}
mes:orders:new:first-page
mes:orders:dashboard:summary
```

TTL:

```text
30–60 секунд
```

TTL используется как страховка от рассинхронизации.

---

## 4. Стратегия обновления кеша

Используется Write-Through подход:

1. Запись идёт в MES DB
2. После успешной записи обновляется Redis
3. Чтение происходит из Redis

Дополнительно используется TTL:

* если кеш не обновился — он автоматически протухнет;
* минимизируется риск устаревших данных.

## 6. Сравнение решений

| Решение           | Плюсы                     | Минусы            |
| ----------------- | ------------------------- | ----------------- |
| Client-side cache | Быстро внедрить           | Не разгружает БД  |
| Cache-Aside       | Простота                  | Несогласованность |
| Write-Through     | Консистентность, контроль | Чуть выше latency |
| Refresh-Ahead     | Быстрое чтение            | Сложность         |

Выбор: **Write-Through**

---

## 7. Риски

* небольшое увеличение latency записи;
* дополнительная инфраструктура (Redis);
* необходимость контролировать размер кеша;
* нельзя использовать кеш как источник истины.

---

## 8. Вывод

Кеширование реализуется через Redis на стороне MES API.
Используется паттерн Write-Through: данные записываются в MES DB и сразу обновляют кеш.
Это снижает нагрузку на базу, ускоряет дашборд и обеспечивает согласованность данных.
