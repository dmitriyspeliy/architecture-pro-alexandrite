# Архитектурное решение по кешированию

## 1. Мотивация

В системе MES наблюдаются проблемы с производительностью: операторы жалуются на долгую загрузку дашборда со списком заказов. Фильтрация и пагинация не дали эффекта, что указывает на высокую нагрузку при чтении данных из БД.

Основные проблемы:

* медленная загрузка списка заказов;
* высокая нагрузка на MES DB;
* задержка появления новых заказов для операторов;
* ухудшение пользовательского опыта.

Кеширование должно:

* ускорить чтение данных;
* снизить нагрузку на базу;
* обеспечить быстрый доступ к новым заказам;
* стабилизировать систему при росте нагрузки.

Кешируются:

* список заказов по статусам;
* первая страница новых заказов;
* агрегаты (количество заказов по статусам).

Не кешируются:

* операции записи (изменение статуса);
* расчёт стоимости;
* критичные транзакции.

---

## 2. Предлагаемое решение

Тип кеширования: серверное.

Технология:

* Redis — внешний кеш;
* MES API — работа с кешем;
* MES DB — источник истины.

Паттерн: **Cache-Aside**

### Почему Cache-Aside

* простая реализация;
* не влияет на запись;
* гибкая инвалидация;
* подходит для read-heavy сценариев.

### Почему не другие

* Write-Through — увеличивает latency записи;
* Refresh-Ahead — сложен для MVP, требует предсказания нагрузки.

---

## 3. Ключи кеша

```text
mes:orders:status:{status}:page:{page}:size:{size}
mes:orders:new:first-page
mes:orders:dashboard:summary
```

TTL:

```text
30–60 секунд
```

---

## 4. Стратегия инвалидации

Используется комбинированный подход:

1. По ключу
   При изменении статуса удаляются связанные записи.

2. TTL
   Автоматическое протухание кеша.

3. Программная
   Явное удаление после записи в БД.

Почему:

* данные часто меняются;
* допустима небольшая задержка;
* минимизируется риск устаревших данных.

## 6. Сравнение решений

| Решение           | Плюсы                        | Минусы            |
| ----------------- | ---------------------------- | ----------------- |
| Client-side cache | Быстро                       | Нет разгрузки БД  |
| Cache-Aside       | Простота, контроль, гибкость | Нужна инвалидация |
| Write-Through     | Консистентность              | Медленная запись  |
| Refresh-Ahead     | Быстрое чтение               | Сложность         |

Выбор: **Cache-Aside**

---

## 7. Риски

* устаревшие данные (решается TTL);
* сложность инвалидации;
* дополнительная инфраструктура (Redis);
* нельзя использовать кеш как источник истины.

---

## 8. Вывод

Кеширование внедряется на уровне MES API через Redis.
Используется паттерн Cache-Aside с TTL и инвалидацией по ключам.
Это решение ускоряет чтение, снижает нагрузку на БД и улучшает UX операторов.
