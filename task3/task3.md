# Архитектурное решение по трейсингу

## 1. Зоны покрытия трейсингом

Трейсингом нужно покрыть весь путь заказа:

1. Online Shop API
   - создание заказа;
   - загрузка 3D-файла;
   - отправка заказа на расчёт.

2. CRM API
   - получение заказа;
   - подтверждение производства;
   - закрытие заказа.

3. MES API
   - расчёт стоимости;
   - взятие заказа в производство;
   - смена производственных статусов.

4. RabbitMQ
   - публикация сообщений;
   - получение сообщений;
   - ошибки обработки;
   - retry/DLQ.

5. S3-хранилище
   - загрузка 3D-модели;
   - получение файла для расчёта.

Основные места зависания:
- заказ создан, но не попал в CRM;
- сообщение ушло в RabbitMQ, но не обработано;
- расчёт цены в MES выполняется слишком долго;
- заказ попал в DLQ;
- статус изменился в MES, но не дошёл до CRM.

---

## 2. Данные для трейсинга

В каждый trace/span нужно добавлять:

- traceId;
- spanId;
- orderId;
- customerId;
- sourceSystem;
- targetSystem;
- orderStatus;
- eventType;
- queueName;
- messageId;
- correlationId;
- errorCode;
- errorMessage;
- duration;
- timestamp.

Важно: персональные данные и содержимое 3D-файлов в trace не писать.

---

## 3. Мотивация

Сейчас команда не видит полный путь заказа между Online Shop, CRM, MES и RabbitMQ. Из-за этого расследование проблем занимает много времени, а бизнес узнаёт о сбоях через жалобы клиентов.

Трейсинг позволит:
- увидеть полный путь заказа между системами;
- быстро понять, где заказ завис;
- связать API-запросы, сообщения RabbitMQ и обработку в MES;
- быстрее расследовать инциденты;
- снизить количество потерянных заказов.

Метрики, на которые повлияет трейсинг:
- среднее время расследования инцидента (MTTR);
- количество потерянных/зависших заказов;
- время прохождения заказа между статусами;
- время расчёта стоимости в MES;
- количество повторных обращений клиентов в поддержку.

---

## 4. Предлагаемое решение

Внедрить распределённый трейсинг на базе OpenTelemetry.

Компоненты:
- OpenTelemetry SDK/agent для Online Shop API;
- OpenTelemetry SDK/agent для CRM API;
- OpenTelemetry SDK/agent для MES API;
- OpenTelemetry Collector;
- Tempo или Jaeger как хранилище трейсов;
- Grafana для просмотра трейсов;
- проброс trace context через HTTP и RabbitMQ.

Техническая схема:
- HTTP-запросы передают `traceparent` header;
- сообщения RabbitMQ содержат `traceparent` и `correlationId` в headers;
- каждый сервис создаёт span при обработке заказа;
- ошибки обработки пишутся в span status/error;
- ключевые бизнес-операции добавляют orderId и orderStatus как span attributes.

Новые компоненты на C4-схеме:
- OpenTelemetry Collector;
- Trace Storage: Tempo/Jaeger;
- Grafana;
- новые связи от Online Shop, CRM, MES и RabbitMQ к OpenTelemetry Collector.

## 5. Автоматический мониторинг прохождения заказа

Дополнительно можно построить контроль процесса заказа на основе trace/span данных.

Идея:
- для ключевых этапов заказа фиксировать spans;
- рассчитывать длительность между статусами;
- строить алерты, если заказ слишком долго находится на этапе.

Примеры алертов:
- заказ находится в SUBMITTED больше 30 минут;
- расчёт цены длится больше 30 минут;
- сообщение попало в DLQ;
- статус изменился в MES, но не дошёл до CRM;
- заказ не перешёл в MANUFACTURING_STARTED за заданное время.

Компоненты:
- OpenTelemetry Collector;
- Tempo/Jaeger;
- Grafana alerts;
- Alertmanager.

Ссылка на диаграмму с алертингом:
- [alexandrite-c4-tracing-alerting.puml](./alexandrite-c4-tracing-alerting.puml)

## 6. Компромиссы

Трейсинг не решит проблему сам по себе. Он только покажет, где заказ ломается или тормозит.

Ограничения:
- старые участки MES на C# могут потребовать ручной доработки;
- RabbitMQ нужно доработать для проброса trace headers;
- при большом трафике потребуется sampling;
- нельзя писать в trace персональные данные и содержимое файлов;
- трейсинг не заменяет бизнес-аудит статусов заказа.

---

## 7. Безопасность

Меры безопасности:

- доступ к Grafana/Jaeger/Tempo только через корпоративную сеть/VPN;
- обязательная аутентификация через корпоративную учётную запись;
- роли доступа: Support, DevOps, Developer, Admin;
- запрет записи персональных данных в trace attributes;
- маскирование customerId при необходимости;
- ограниченный срок хранения трейсов;
- аудит доступа к системе трейсинга;
- закрытый доступ извне.

---

## 8. Вывод

Трейсинг нужен, чтобы видеть полный путь заказа через Online Shop, CRM, MES и RabbitMQ.  
Он не заменяет мониторинг и логи, но позволяет быстро ответить на главный вопрос: где сейчас заказ и на каком этапе он завис.
