# Архитектурное решение по логированию

## 1. Какие системы покрываем логированием

В первую очередь логирование нужно настроить для:

1. Online Shop API  
   Здесь создаётся заказ, загружается 3D-модель и начинается клиентский сценарий.

2. CRM API  
   Здесь заказ подтверждается, закрывается и используется менеджерами.

3. MES API  
   Здесь рассчитывается цена и меняются производственные статусы.

4. RabbitMQ  
   Через очереди проходят события между CRM и MES. Потеря или ошибка обработки сообщения напрямую влияет на заказ.

5. API для внешних партнёров  
   После открытия B2B API выросла нагрузка и количество жалоб.

---

## 2. INFO-логи

На уровне INFO нужно логировать бизнес-события:

- создание заказа;
- загрузка 3D-модели;
- отправка заказа на расчёт цены;
- успешный расчёт цены;
- изменение статуса заказа;
- подтверждение производства;
- взятие заказа оператором в работу;
- завершение производства;
- отправка заказа клиенту;
- закрытие заказа;
- публикация сообщения в RabbitMQ;
- успешная обработка сообщения из RabbitMQ.

Обязательные поля:

- timestamp;
- service;
- traceId;
- spanId;
- orderId;
- customerId или partnerId;
- eventType;
- orderStatus;
- messageId;
- queueName;
- durationMs;
- result.

---

## 3. Другие уровни логирования

- DEBUG — только временно при расследовании инцидентов, в production по умолчанию выключен.
- WARN — нестандартная ситуация без падения: повторная обработка сообщения, долгий расчёт, превышение SLA.
- ERROR — ошибка бизнес-операции или технический сбой: заказ не обработан, сообщение ушло в DLQ, недоступна БД, ошибка интеграции.
- FATAL/CRITICAL — недоступность сервиса или потеря критичного бизнес-процесса.

---

## 4. Мотивация

Сейчас команда разбирает проблемы со слов клиентов. Это долго и ненадёжно.

Централизованное логирование позволит:

- быстро находить, что произошло с заказом;
- расследовать ошибки без ручного опроса клиента;
- снизить нагрузку на поддержку;
- быстрее исправлять дефекты;
- видеть повторяющиеся проблемы в API, MES, CRM и RabbitMQ.

Метрики, на которые повлияет логирование:

- MTTR — среднее время расследования инцидента;
- количество обращений в поддержку;
- количество потерянных или зависших заказов;
- доля ошибок при обработке заказов;
- время обработки инцидентов второй линией поддержки.

---

## 5. Приоритет внедрения

Первый приоритет:

1. MES API  
   Потому что здесь расчёт цены и производственные статусы.

2. RabbitMQ  
   Потому что сообщения могут теряться, зависать или попадать в DLQ.

3. CRM API  
   Потому что здесь подтверждение и закрытие заказов.

4. Online Shop API  
   Потому что здесь начинается клиентский заказ.

5. B2B API  
   Потому что внешние партнёры создают дополнительную нагрузку.

Логирование и трейсинг нужно внедрять сначала в MES + RabbitMQ, потому что именно там чаще всего заказ может зависнуть между системами.

---

## 6. Предлагаемое решение

Предлагается внедрить централизованное структурированное логирование.

Технологии:

- JSON logs во всех сервисах;
- Loki или OpenSearch как хранилище логов;
- Promtail / Fluent Bit для сбора логов;
- Grafana для поиска и дашбордов;
- Alertmanager для алертов.

Схема работы:

1. Online Shop, CRM и MES пишут JSON-логи в stdout.
2. Fluent Bit собирает логи с инстансов.
3. Логи отправляются в Loki/OpenSearch.
4. Grafana используется для поиска по orderId, traceId, service, status.
5. По критичным паттернам настраиваются алерты.

Новые компоненты на схеме:

- Fluent Bit / Promtail;
- Loki или OpenSearch;
- Grafana Logs UI;
- Alertmanager.

Ссылка на диаграмму:

- `./alexandrite-c4-logging.puml`

---

## 7. Безопасность

В логи запрещено писать:

- паспортные данные;
- банковские данные;
- полный адрес клиента;
- телефон и email в открытом виде;
- содержимое 3D-файлов;
- токены авторизации;
- пароли и секреты.

Правила:

- customerId и partnerId можно писать как технические идентификаторы;
- персональные данные маскировать;
- доступ к логам только через корпоративную учётную запись;
- роли доступа: Support, Developer, DevOps, Admin;
- аудит доступа к логам обязателен;
- внешнего публичного доступа к логам быть не должно.

---

## 8. Политика хранения

Предлагается разделить логи по индексам:

- `shop-api-logs`;
- `crm-api-logs`;
- `mes-api-logs`;
- `rabbitmq-logs`;
- `b2b-api-logs`.

Срок хранения:

- ERROR/WARN — 90 дней;
- INFO — 30 дней;
- DEBUG — не более 7 дней и только временно.

Для экономии места старые логи архивируются или удаляются по retention policy.

---

## 9. Анализ логов и алертинг

Нужно настроить алерты:

- рост количества ERROR по сервису;
- появление сообщений в DLQ;
- резкий рост заказов через B2B API;
- заказ завис в одном статусе дольше SLA;
- ошибка расчёта цены в MES;
- повторяющиеся ошибки обработки RabbitMQ-сообщений.

Аномалии:

- резкий скачок количества созданных заказов;
- резкий рост HTTP 500;
- массовые ошибки от одного партнёра;
- необычно большое количество повторных запросов.

## 10. Выбор технологии

| Критерий | Loki | OpenSearch | ELK |
|---|---|---|---|
| Стоимость | низкая | низкая | средняя/высокая |
| Простота внедрения | высокая | средняя | средняя |
| Поиск по полям | базовый | сильный | сильный |
| Интеграция с Grafana | отличная | хорошая | хорошая |
| Требования к ресурсам | ниже | выше | выше |
| Подходит для MVP | да | да | скорее избыточно |

Выбор для MVP: **Loki + Grafana + Fluent Bit**.

Причина: решение проще и дешевле для внедрения, хорошо подходит для Kubernetes и быстро закрывает основную задачу — поиск логов по `orderId`, `traceId` и сервису.

OpenSearch можно рассмотреть позже, если потребуется сложный полнотекстовый поиск и аналитика по большим объёмам логов.

---

## 11. Вывод

Логирование нужно внедрять как централизованную систему анализа событий по заказам.  
Главная цель — быстро отвечать на вопрос: что произошло с заказом, в каком сервисе возникла ошибка и кто должен её исправлять.
