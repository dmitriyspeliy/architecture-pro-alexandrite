# Планирование: анализ, идентификация проблем и поиск решений

## 1. Проблемы

1. Single point of failure  
   Все сервисы и БД в одном инстансе → падение = недоступность системы.

2. Нет наблюдаемости  
   Нет метрик, трейсинга, централизованных логов → проблемы находят клиенты.

3. Потеря/задержка заказов  
   Нет контроля очередей (RabbitMQ), статусы размазаны по системам → сложно понять, где заказ.

4. Медленный MES-дэшборд  
   Тяжёлые запросы → операторы не видят новые заказы → простой.

5. Долгий расчёт цены  
   До 30 минут → растёт backlog, нет контроля SLA.

6. B2B нагрузка ломает B2C  
   Нет rate limiting и изоляции API → партнёры перегружают систему.

7. Медленные релизы  
   Ручной QA → баги долго чинятся.

8. Общая база Shop и CRM  
   Shop API и CRM используют одну БД → сильная связанность.  
   Нельзя независимо масштабировать сервисы, нагрузка CRM влияет на B2C, изменения схемы рискованны.

9. Нет выделенного B2B API  
    Внешние партнёры работают через тот же контур → нет rate limiting и изоляции нагрузки.

---

## 2. Инициативы

P0:
- Внедрить мониторинг + алерты + логи + трейсинг
- Нормализовать жизненный цикл заказа (event-driven, idempotency, retry, DLQ)
- Оптимизировать MES-дэшборд (индексы, read-модель, кеш)

P1:
- Масштабировать сервисы (несколько инстансов + LB)
- Разделить B2C/B2B (API Gateway + rate limit)
- Оптимизировать БД (индексы, read-replica)

P2:
- Автоматизировать тесты и релизы

## 2.1. Ключевые быстрые инициативы (top-3)

Если делать только самое критичное:

1. Rate limiting + изоляция B2B
2. Базовые метрики + алерты
3. Трейсинг прохождения заказа

---

## 3. Приоритизация

Логика:
- сначала понять проблему → наблюдаемость
- затем убрать потери заказов → статусная модель
- затем ускорить операционный контур → MES

Порядок:
1. Наблюдаемость
2. Поток заказов (очереди + статусы)
3. MES-дэшборд
4. Масштабирование
5. B2B изоляция
6. БД
7. CI/CD

---

## 4. Целевая архитектура (6 месяцев)

- Все сервисы масштабируются (multi-instance)
- Очереди с retry/DLQ и мониторингом
- Единый поток событий по заказу
- Быстрый MES-дэшборд (read-модель/кеш)
- API Gateway для внешних клиентов
- Полная наблюдаемость (метрики, логи, трейсы)

## 5. Метрики (что измеряем)

API:
- RPS по сервисам (shop, CRM, MES, B2B)
- HTTP 500 по сервисам
- latency p95/p99

RabbitMQ:
- messages in flight
- DLQ size
- processing time

Бизнес:
- время прохождения заказа
- количество зависших заказов
- SLA расчёта цены

Система упёрлась не в ресурсы, а в **отсутствие контроля и прозрачности**.  
Сначала делаем наблюдаемость и порядок в заказах, потом масштабируем.
